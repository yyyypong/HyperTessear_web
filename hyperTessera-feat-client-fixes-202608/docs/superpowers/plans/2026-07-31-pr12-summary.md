# PR #12 summary — vault-local/asset-local RBAC + NAVOracle/RWAAdapter redesign

Full change set on `feat/vault-local-rbac` vs `main`: 104 files changed
(~25.8k insertions, ~9.9k deletions) across contracts, tests, the off-chain
module, deploy scripts, and the control panel.

## 1. NAVOracle/RWAAdapter redesign

The original vault-centric `NAVOracle` (wired per-Vault through
`StateManager`) is replaced with a standalone, token-keyed oracle:

- `INAVOracle`/`NAVOracle` rewritten around a `PriceData { price,
  dataTimestamp, updatedAt }` struct keyed by RWA token address, with
  owner-managed per-token signers and EIP-712 signature verification
  (replacing `eth_sign`). Permissionless relay — anyone can submit an
  update as long as it carries a valid signature from that token's
  authorized signer.
- No more `StateManager`/Vault dependency — integrated instead with a new
  `RWAAdapter` (`src/asset-management/strategy/RWAAdapter.sol`), which
  values RWA token balances via the new oracle. Deployed through
  `AdapterFactory.deployRWAAdapter`.
- `Deploy.s.sol` reworked: `NAVOracle` now constructs with just a governor
  address (no vault-keyed wiring); the old `DemoNAVConsumer` placeholder is
  deleted in favor of a real local-devnet `RWAAdapter` demo deployment;
  `DeployW3`'s now-incompatible `_wireNAV` helper is dropped.
- Off-chain: the NAV SDK surface is token-keyed end to end (`sdk.ts`,
  `indexer.ts`'s `navByVault` renamed to `navByToken`), NAV-staleness
  alerting removed from `keeperBot.ts` (no longer meaningful for a
  permissionless, per-token oracle), `control-panel`'s NAV UI migrated to
  the token-keyed API, and the local-devnet e2e wiring points at the real
  `RWAAdapter` demo instead of the deleted `DemoNAVConsumer`.
- 28 new `NAVOracleTest` cases plus a new `RWAAdapter.t.sol` suite.

## 2. Vault-local / asset-local RBAC redesign (角色权限与职责修改方案)

Replaces the single protocol-wide role registry with a two-tier model:

- `HyperAccessControl` now only holds `GOVERNOR_ROLE` (protocol infra
  upgrades, module-level emergency pause).
- Every other role — Curator, Guardian, Allocator, Settlement Operator,
  Keeper — is now **Vault-local**, appointed by that Vault's own Owner
  through a new `IVaultRoles` interface implemented by `BaseVault`.
- Asset-side roles (Issuer, Token Agent, Proof Publisher, Wrapper
  Controller) are now **per-assetId**, tied to that asset's `AssetRegistry`
  owner.
- New per-Vault `VaultTimelock` (`src/governance/VaultTimelock.sol`)
  replaces the deleted global `ProtocolTimelock`: Owner/Curator-class
  parameter changes are direct while a Vault is `CONFIGURING`, then
  Timelock-gated afterward.
- New minimal `AdapterRegistry` — each Vault whitelists which Adapter
  implementations its Curator is allowed to attach.
- `VaultFactory`/`AdapterFactory` deployment is now permissionless.
- `UnifiedPool` deposits (`repayInterest`/`repayPrincipal`) are now
  permissionless and no longer fix Vault attribution at deposit time; new
  `attributeInterest`/`attributePrincipal`, gated to that Vault's
  Settlement Operator, do the attribution afterward.

**Bundled in the same commit:** an initial-settlement timing fix —
deposits made during the `SUBSCRIBING` window previously had to wait a
full cycle duration before being settled. `StateManager.finalizeSubscription`
now routes a successful raise straight into cycle 0 `CALCULATING` instead
of `ACCEPTING`, so Settlement can immediately snapshot/settle/complete that
cycle and mint the first cohort's shares (standard 1 USDT : 1 share
zero-supply price) before normal Cycle 1 operations begin.

**Follow-up fix:** `VaultFactory`'s constructor was `new`-ing
`EarnVaultDeployer`/`LiquidityEarnVaultDeployer` inline, which transitively
embedded the full Vault contracts' creation bytecode into `VaultFactory`'s
own init code — this exceeded the EIP-3860 max-initcode-size limit once the
RBAC refactor grew the Vaults' bytecode. Fixed by deploying the two
deployers independently and passing their addresses into the constructor.

## 3. Compliance-audit follow-up fixes

An independent audit of the RBAC redesign against the delivery spec
surfaced 5 gaps, each fixed in its own commit:

1. **Keeper fallback removal** — `BaseVault.isKeeper`/`_onlyKeeper`: Owner
   no longer implicitly counts as Keeper; must be granted explicitly via
   `setKeeper(account, true)`. The delivery deploy script already does
   this for `governor`.
2. **`addAdapter` `realAssets()` check** — `BaseVault.addAdapter` now calls
   `IAdapter(adapter).realAssets()` once at admission, so a malformed
   Adapter reverts at admission instead of silently bricking the Vault
   later.
3. **`claimingEnd` gate** — new `ProductParams.claimingEnd` field;
   `StateManager.closeProduct` now reverts with
   `ConditionNotMet("claimingEnd not reached")` until
   `block.timestamp >= claimingEnd`.
4. **Final-settlement confirmation gate** — new
   `StateManager.completeFinalSettlement`/`isFinalSettlementComplete`:
   `enterMaturing` now reverts until a Vault's Settlement contract has
   confirmed final settlement via the new
   `Settlement.confirmFinalSettlement(vault, signatures)` entry point
   (M-of-N Settlement Operator signatures, permissionless relaying — same
   trust model as `submitBatch`). A new
   `Settlement.hashFinalSettlementConfirmation(vault)` view mirrors
   `hashInstruction` so off-chain code can fetch the exact hash to sign.
5. **Zero-threshold guard** — `Settlement._validateSignatures` now reverts
   with `SignatureValidationFailed` if a Vault's operator threshold was
   never configured (`threshold == 0`), instead of silently accepting an
   empty signature array. Affects both `submitBatch` and
   `confirmFinalSettlement`.

**Off-chain follow-up for fix 4:**
- `sdk.ts` — `hashFinalSettlementConfirmation`, `isFinalSettlementComplete`,
  `confirmFinalSettlement` wrappers.
- `settlementOperator.ts` — new `confirmFinalSettlement(vault, relayer)`
  pipeline: collects M-of-N operator signatures over the confirmation hash
  and submits with retry/backoff.
- `keeperBot.ts` — new `"final-settlement-pending"` alert type, fired when
  a Vault is `SETTLING` but final settlement hasn't been confirmed yet.
  KeeperBot deliberately does not call `confirmFinalSettlement` itself —
  that stays `SettlementOperator`'s job (a different signing key set).

A subsequent review pass (`b309521`) caught and fixed stale control-panel
ABIs, doc drift, and an unauthenticated zero-threshold signature path left
over from the initial fix; `1b7d3a0` regenerated control-panel ABIs after
`hashFinalSettlementConfirmation` was added; `8483103` retargeted a vacuous
cycle-transition test and dropped an unsafe `any`-cast on RPC URL
introspection in the off-chain code.

## 5. Other real bugs found during migration

- `LiquidityBridge.bridgeDeposit`'s authorization check called
  `allocator()` unconditionally instead of short-circuiting behind the
  cheaper `msg.sender == fromVault` check — this broke every real
  `LiquidityAdapter.bridgeToCash` call, since `fromVault` is the Adapter
  itself and doesn't implement `IVaultRoles`.

## 6. Test infrastructure fixes

- `offchain/test/deployStack.ts` (the vitest integration-test harness
  backing `npm run test:integration`) rewritten to deploy via the real
  delivery scripts (`Deploy` → `DeployW3` → `DeployW4` via `forge script
  --broadcast`) instead of a drifted hand-rolled TS reimplementation. Also
  fixes a pipe-blocking bug (anvil's stdout/stderr weren't drained, which
  stalls mining once the OS pipe buffer fills) and a stale cycle-0
  assertion in the e2e test.
- `offchain/scripts/local/deploy.ts` — fixed a deterministic nonce race in
  the vault-local role-wiring step (`setCurator`/`setGuardian`/
  `setAllocator`): its ad hoc `JsonRpcProvider` used ethers' default
  request batching, which raced `eth_getTransactionCount` ahead of prior
  sends despite being awaited sequentially. Pinned `batchMaxCount: 1` to
  match the fix `config.ts` already applies to the SDK's own provider.
  (Found and fixed during a manual local-anvil end-to-end verification
  pass — see `2026-07-31-anvil-e2e-report.md` in this directory for the
  full walkthrough of the SETTLING → confirmFinalSettlement → MATURING →
  CLAIMING → CLOSED tail this branch added.)
